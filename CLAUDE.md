# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `bun install` — install deps (postinstall may prompt to trust `agent-browser`/`playwright-core`; run `bun pm trust agent-browser playwright-core` if `bun pm untrusted` lists them, so Playwright's browser binary install runs). Also applies `patches/playwright-core@1.61.1.patch` (see below).
- **Playwright + Bun CDP patch (`patches/playwright-core@1.61.1.patch`, wired via `patchedDependencies`):** Playwright's bundled `ws` (`require("./utilsBundle").ws`) is patched to the standalone `ws` package (`require("ws")`, an explicit dep). Under Bun 1.3.x the bundled `ws` mis-handles the WebSocket upgrade (HTTP 101) and throws `Unexpected server response: 101` instead of firing `open`, so `chromium.connectOverCDP()` hangs and every agent's browser attach dead-ends with a generic "Failed to connect via CDP". Node is unaffected — this is Bun-specific. Do NOT remove `ws` from deps or the patch. `bun patch --commit` fails on Windows with `EPERM ... renaming patch file to patches dir`, so the patch file was authored by hand (via `git diff`) rather than by bun — regenerate the same way if playwright-core is bumped.
- `docker compose up -d` — starts Redis + Postgres, mapped to host ports `6380`/`5433` (not the defaults — deliberately remapped so this project doesn't collide with other local Postgres/Redis instances; `.env`/`.env.example` already point at these ports).
- `bun run db:push` — push Drizzle schema to Postgres (`drizzle-kit push`).
- `bun run dev` / `bun run start` — run the app (`bun --env-file=.env run src/index.ts`).
- `bun run typecheck` — `tsc --noEmit`.
- `bun test` — run the full suite (Bun's native test runner, not vitest/jest).
- `bun test tests/unit/commands/dispatch.test.ts` — run a single test file. `bun test -t "name"` filters by test name.
- Local data files: `cp resume.example.md resume.md` and `cp profile.example.json profile.json`, then fill in real details. Both are gitignored (contain personal data).

## Architecture

Single Bun process — TUI, browser session, command dispatch, and all three agents/queues run in one process. No separate HTTP server.

**Runtime constraints (do not violate):**
- Browser is **always visible** (`headless: false`, hardcoded everywhere). No headless config/toggle anywhere in this codebase.
- No LinkedIn/Gmail credentials are ever read, stored, or requested by the app. Login is always manual, in the visible browser window that Playwright opens at startup — LinkedIn in tab 0, Gmail in tab 1. Gmail login is optional and currently vestigial (was originally intended for the external-apply agent, which no longer exists) and never gates `/verify-login`'s unlock, which still checks LinkedIn only.
- Bun throughout — scripts use `bun run`, not `tsx`/`node` (except the browser subprocess, which Bun spawns as a plain Node child process — see below).
- Postgres only, via `drizzle-orm/node-postgres` (`src/db/`). No SQLite/libsql.
- Test runner is `bun test`, not vitest — vitest's oxc transform rejects the `jsx: "preserve"` + `jsxImportSource: "@opentui/solid"` tsconfig combination this project requires. `@opentui/solid` ships a `bun-test-node` shim specifically for `bun test`.

**Browser bootstrap (`src/browser/session.ts` + `scripts/browser-server.mjs`):** the main process does **not** drive Playwright directly. At startup it spawns `scripts/browser-server.mjs` as a Node child process (`Bun.spawn`), which launches a visible `chromium.launchPersistentContext` and exposes it over a tiny local HTTP API (`/navigate`, `/newtab`, `/check-selector`, `/page-url`, `/cdp-url`, `/state`, `/close`) on a port it reports back via stdout (`READY:<port>`). `session.ts` talks to that subprocess over `fetch()`. `getSharedCdpUrl()` returns the browser's real CDP endpoint (discovered by polling the Chromium profile's `DevToolsActivePort` file) — this is what later agent phases attach to via `@mastra/agent-browser`'s `AgentBrowser({ cdpUrl, scope: 'shared' })`, so every agent shares the one browser you logged into. This subprocess/HTTP-API design is a deliberate deviation from the original plan (which had the main process call `agent-browser`'s `BrowserManager` directly) — see `docs/superpowers/plans/2026-07-14-phase1-foundation.md` Task 5 for the superseded version and `docs/superpowers/specs/2026-07-14-tui-rebuild-design.md` for the still-current data/queue/phase design. `saveState()` in `browser-server.mjs` must `await browser.cookies()` — it's an async Playwright call; calling it without `await` silently serializes the pending Promise (`{}`) instead of the cookie array, which is why login state can silently fail to persist across restarts if this regresses.

`launchPersistentContext` passes `channel: 'chrome'` (uses the system-installed Chrome stable binary, not Playwright's bundled Chromium — needed so Google's sign-in doesn't show "This browser or app may not be secure"), plus `args: ['--disable-blink-features=AutomationControlled']` and `ignoreDefaultArgs: ['--enable-automation']` to strip the `navigator.webdriver` automation fingerprint that same check looks for. `--no-sandbox` was deliberately removed from `args` — it's a Linux-root/Docker concern, not Windows, and its only effect here was an unnecessary "unsupported command-line flag" banner. `openLoginTabs(linkedinUrl, gmailUrl)` opens LinkedIn in the default tab (index 0) via `/navigate` and Gmail in a second tab (index 1) via `/newtab` — tab indices are load-bearing: `verifyLogin()` assumes this fixed ordering.

**State (`src/state/`):** a Solid store (`app-state.ts`) is the single source of truth — `session` (login status), `activeTab`, per-tab `TabState` (status/step/logs/needsInputQuestion), and `settings`. All mutation goes through its exported setters (`setSessionStatus`, `pushLog`, `setAgentStatus`, `setNeedsInput`, `setSetting`), never by reaching into the store directly — `@opentui/solid`'s reactivity depends on going through the store's own setter (`produce`/path-set), not `.push()` on a store-derived array.

**Commands (`src/commands/`):** a name→handler registry (`registry.ts`) scoped `'global' | TabId`. `dispatch.ts` parses `/name args`, rejects unknown commands, and — critically — rejects any non-global command until `isUnlocked()` (i.e. `/verify-login` has succeeded), directing the user back to `/verify-login`. `global-commands.ts` holds the always-available commands (`/help`, `/tab`, `/set`, `/reload-config`, `/verify-login`, `/exit`); `search-commands.ts` (`/search-urls`, `/stop-search`, `/auto-on`, `/auto-off`), `easy-commands.ts` (`/process-easy-queue`, `/stop-easy-queue`), `judge-commands.ts` (`/process-judge-queue`, `/stop-judge-queue`), and `career-commands.ts` (`/add-career-url`, `/check-careers`, `/stop-careers`) hold the tab-scoped command sets. There is no `external-commands.ts` — external jobs are never queued/worked, so there's nothing to start/stop for that tab (the TUI's `external` tab itself was removed for the same reason — see the scan/judge split below). All wired into `registerBuiltinCommands()` (`src/commands/index.ts`) — there's no stub-commands module anymore, every planned command is real.

**Needs-input / prompt channel (`src/state/prompt-channel.ts`):** generic, tab-scoped human-in-the-loop mechanism, used by all three agents. `waitForAnswer(tab, question)` sets the tab's `needsInputQuestion` (sidebar highlights it) and returns a promise that resolves when `answerPrompt(tab, answer)` is called. `InputBar` checks `appState.tabs[activeTab].needsInputQuestion` and switches from command mode to plain-text answer mode whenever it's set, routing the typed reply to `answerPrompt` instead of `dispatchCommand`. Search's `request-human-input` and the easy-apply agent's `ask-human-and-remember` tools all await `waitForAnswer` to pause on a genuinely stuck case (LinkedIn checkpoint, CAPTCHA, unknown form question, email verification) instead of crashing.

**TUI (`src/tui/`):** `@opentui/solid`, styled after opencode's theme (`theme.ts`). `App.tsx` composes `Header` (session status) / `Sidebar` (per-agent status, scrollable, collapses on narrow terminals) / `LogPanel` (active tab's log lines) / `InputBar` (command input, disabled with a placeholder until login is verified). Tab/Shift+Tab cycles the four tabs (`search`/`easy`/`judge`/`careers`); **Ctrl+Q** exits (`/exit`). **Ctrl+C copies the current selection** (App.tsx `copySelection` → `renderer.copyToClipboardOSC52`), and a drag-selection auto-copies on release (`useSelectionHandler`) with a "Copied to clipboard" toast (`components/Toast.tsx`). This requires `createCliRenderer({ exitOnCtrlC: false })` (`index.tsx`) — otherwise opentui's built-in Ctrl+C handler destroys the renderer before `useKeyboard` sees the key. Selection uses opentui's OWN mouse selection (mouse reporting left on, the default), NOT terminal-native selection — the latter can't work in a 30fps-repainting TUI. **Layout must be sized off `useTerminalDimensions()`, not `height="100%"`:** the root box binds `width={dimensions().width} height={dimensions().height}` (like opencode) — `height="100%"` resolved against a root height that was wrong on first paint, so the whole layout was broken (content spilling below the TUI, empty bottom half with a stray scrollbar) until a terminal resize delivered real dimensions. Fixed-height chrome (`Header`, `InputBar`) is wrapped in `flexShrink={0}` boxes; both `scrollbox`es also pass `viewportCulling={false}` and App.tsx nudges `renderer.requestRender()` on log-length change as belt-and-suspenders. `index.tsx` owns the `CliRenderer` lifecycle (`mountTui`/`destroyTui`) — must stay `.tsx` (Bun's transform can't parse JSX in a plain `.ts` file).

**Config & profile:** `linkedin-auto.config.ts` (zod-validated via `src/config/schema.ts`/`loader.ts`) holds `urlGroups` (named groups of `{ url, scanFullList }` entries — replaces the old flat `mustCheckUrls`), requirements text, concurrency, `model` (default/fallback), `models` (per-agent overrides: `search`/`easyApply`/`career`/`judge`), and `profileFiles` paths — no `headless` field, ever. `src/config/current.ts` holds the loaded `AppConfig` as a module-level singleton (`setCurrentConfig`/`getCurrentConfig`, set once in `src/index.ts`, re-set live by `/reload-config` — see below) so commands/agents can read `urlGroups`/`requirements`/`profileFiles`/`models` without threading config through every call. `model` is also copied into `appState.settings` at startup; `/set model <x>` updates that live copy. Each agent resolves its model via `resolveModel(config, appState.settings.model, agentKind)` (`src/config/resolve-model.ts`) — an explicit `config.models[agentKind]` override wins, otherwise it falls back to the live `appState.settings.model`. `/reload-config` (`global-commands.ts`) re-runs `loadConfig()` and swaps `getCurrentConfig()`'s backing config on success (keeps the old one on a validation failure); it does NOT touch `appState.settings` — `/set`'s live overrides (concurrency/model/nav-delays) are a separate path. `resume.md` (free text) + `profile.json` (structured, zod-validated via `src/profile/`) are the user's real data, gitignored, loaded fresh at the start of every run (not just at startup) so edits take effect immediately — no `/reload-config` needed for those two files; `profile.json.answers` is the durable store for learned form-answer Q&A, written by the easy-apply agent's `ask-human-and-remember` tool.

**DB (`src/db/`):** Drizzle schema (`jobs`, `applications`, `search_runs`, `career_pages`, `career_page_scans`, `answer_reviews`). `jobs`/`search_runs` are written by the LinkedIn search agent (`src/agents/search-agent.ts`); `career_pages`/`career_page_scans` and career-sourced `jobs` rows by the career-scan agent (`src/agents/career-scan-agent.ts`); `applications` only by the easy-apply agent (`easy-apply-agent.ts`) — there is no apply automation for external jobs, so they never get an `applications` row, only a `jobs` row with `status: 'external_saved'`. Job dedupe across repeated LinkedIn search runs works by primary key: `jobs.id` is the job's numeric LinkedIn id, checked via the `check-already-seen` tool before it's recorded. Career postings dedupe the same way via `check-posting-seen`, keyed by a hash of the apply URL (`applyUrlToJobId`) — this is a reversal from the original design, which deliberately re-judged every posting on every run; that turned out to waste LLM tokens re-judging jobs already recorded. `processEasyApplyJob` re-checks `jobs.status` before doing any work, so a job requeued or double-delivered by BullMQ is a no-op, not a duplicate application.

**Queues (`src/queues/`):** `connection.ts` exposes plain Redis connection options — not an `IORedis` instance, since BullMQ vendors its own `ioredis` and a cross-version instance fails to typecheck. Two BullMQ queues: `apply-queues.ts` (`enqueueApplyJob(jobId)`, `getApplyQueueCounts()`, queue name `easy-apply`) and `judge-queues.ts` (`enqueueJudgeJob(jobId, sourceUrl)`, `getJudgeQueueCounts()`, queue name `job-judge`) — there is no external queue; career-scan-agent's external branch inserts a `jobs` row with `status: 'external_saved'` and calls `recordExternalJobFound()` directly instead of queuing anything. `judge-queues.ts` uses the LinkedIn job id itself as BullMQ's own `jobId` option — re-enqueuing the same id while it's still waiting/active in that queue is then a no-op, which is what makes it safe for the scan loop (below) to push a job id every time it sees one without checking the queue first. `easy-apply-worker.ts` and `judge-worker.ts` are each the sole consumer of their queue — one BullMQ `Worker` apiece (`concurrency: 1`), started/stopped by `/process-easy-queue`+`/stop-easy-queue` and `/process-judge-queue`+`/stop-judge-queue` respectively, wrapping `processEasyApplyJob`/`processJudgeJob`. `easy-apply-worker.ts` additionally computes queue-remaining and applied-today counts per job and folds them into `setAgentStatus('easy', 'running', step)` — no dedicated sidebar state fields for this.

**Mastra (`src/mastra/index.ts`):** a real `Mastra` instance backed by `@mastra/pg`'s `PostgresStore` (requires an `id` in its config, easy to miss; also exported standalone as `storage` in case something needs the store directly without going through `mastra`).

**Search/scan/judge is a three-stage pipeline (`docs/superpowers/specs/2026-07-26-scan-judge-split-design.md`), not one long-running LLM agent.** It replaced an earlier design where a single navigating `Agent` browsed a search URL, judged, and paginated all inside one `agent.generate()` call — that agent could (and in production did) silently stop mid-page with jobs still pending, since the model finishing its turn early looks identical to a completed page (no exception, no timeout). The fix wasn't a better prompt or a bigger watchdog, it was removing the LLM from the scan path entirely:

1. **Scan (`src/agents/search-agent.ts`) — fully deterministic, zero LLM calls.** `runSearchUrls`/`runSearchUrlsInner` open each configured `urlGroups` URL in its own tab (`openOwnTab`/`closeOwnTab`/`reclaimOwnTab` from `tab-guard.ts`, on the same shared bootstrap browser career-scan-agent also uses) and walk it with plain async code, no `Agent`/`createTool`/`generate()` anywhere in this file. Per page: `collectPageIds()` scrolls and reads `[data-occludable-job-id]`/`[data-job-id]` DOM attributes directly (`page.evaluate`), `filterUnseenJobIds()` does one batch `id IN (...)` dedupe query per page (not one query per id), and every new id is handed to `enqueueJudgeJob(id, sourceUrl)` (`judge-queues.ts`) — nothing about a job's content is ever read at scan time. Pagination uses LinkedIn's own `&start=N` URL param (`N = pageIndex * FULL_PAGE_SIZE`) instead of locating and clicking a "Next" control — deterministic, no selector to miss.
   - **Scroll correctness (`collectPageIds`/`scrollAndCollectOnePass`):** every page holds exactly `FULL_PAGE_SIZE` (25) job cards except a genuine last page. The list is virtualized even within one loaded page (only near-viewport cards exist in the DOM), so a `goto` alone doesn't render all of them — scrolling by half the scrollable container's height between reads (`scrollByFraction`) gives 50% overlap between consecutive reads, which is what stops a card from existing only in a "gap" between two scroll positions. The stop condition requires BOTH the container genuinely reaching its scroll bottom AND two consecutive reads adding zero new ids (`shouldStopScrolling`) — either signal alone risks a false-early stop. If the result still undercounts `FULL_PAGE_SIZE` without a hard end-of-results signal (`shouldRetryPageCollection`), one retry pass runs with quarter-height steps as a finer-grained backstop — bounded to at most 2 passes total.
   - **Last-page detection (`isLastPage`/`isDuplicatePage`):** a page is last if it came back with zero cards, if every one of its ids already appeared on the immediately previous page (LinkedIn clamping an out-of-range `start=` back to its last valid page), or if its count is under `FULL_PAGE_SIZE` after the retry pass. `MAX_PAGES_PER_URL` (200) is a hard circuit breaker in case this logic is ever wrong, same role `maxSteps` plays for the agents below.
   - **Checkpoint/CAPTCHA detection (`detectCheckpointUrl`)** is a plain regex against the tab's own URL (`/checkpoint/`, `/authwall`) — no LLM judgment needed to recognize it. On a hit, the loop calls `waitForAnswer` (prompt channel) and retries the same page once answered; nothing is lost because nothing was ever held in an LLM's context.
2. **Judge queue (`src/queues/judge-queues.ts` + `judge-worker.ts`)** — one job id at a time, own dedicated Chrome process (`src/browser/judge-session.ts`, a third browser alongside the bootstrap and easy-apply ones, same cookie-seeding-from-bootstrap pattern as `easy-apply-session.ts`). `processJudgeJob(jobId, sourceUrl)` re-checks the `jobs` table first (idempotency against duplicate delivery), opens `https://linkedin.com/jobs/view/{jobId}/` **directly** via `openOwnTab` (no click-through from a list), reads the detail pane (`browser.snapshot({ interactiveOnly: false })`, retried once after a fixed pause since nothing is driving "is this loaded yet" judgment), then hands that text to `judgeJob()` (`src/agents/job-relevance-judge.ts`, unchanged) — a **fresh `Agent` + a single `generate()` call**, no browser, no tools, no shared conversation with any other job. `recordJudgeVerdict()` (exported, DB-only, directly unit-testable without a browser) does the insert + routing: `applyType: 'easy'` → `status: 'queued'` + `enqueueApplyJob`; `applyType: 'external'` → `status: 'external_saved'` + `recordExternalJobFound()`; `verdict: 'skip'` → `status: 'skipped'`. A posting whose `applyType` is `'easy'` but which ALSO advertises a separate external/company-site link gets a **second** `jobs` row (keyed by `applyUrlToJobId`, shared with career-scan-agent). **Error handling is deliberately split by failure kind:** a transient page-load/snapshot failure (never got far enough to judge) writes **no DB row at all**, so the id stays "unseen" and is naturally retried by a future scan cycle; a `judgeJob()` call itself throwing/returning unparseable output **is** written as a safe `status: 'skipped'` row, since that's a real judgment attempt that failed, not a load hiccup.
3. **Easy-apply (`easy-apply-agent.ts`/`easy-apply-worker.ts`)** — unchanged, still fed by whatever `enqueueApplyJob` calls arrive, whether from the judge worker (current) or the old inline tool (superseded).

`urlGroups` entries still carry a `scanFullList` flag in the config schema for back-compat with existing config files, but it's a no-op — there's nothing left for it to bypass; every URL is always walked to its genuine end (or `MAX_PAGES_PER_URL`).

**Auto mode (`search-scheduler.ts`)** starts both `easy-apply-worker.ts` and `judge-worker.ts` once per app session (`ensureApplyWorkersRunning`, idempotent), not per cycle — a loop/interval cycle now only drives the fast deterministic scan; the judge queue drains independently in the background, so a slow judge-worker page load never blocks the next scan cycle from starting.

**Easy-apply agent (`src/agents/easy-apply-agent.ts`):** the only remaining apply-automation agent — there is no external-site equivalent (see below). Its own singleton `AgentBrowser`, one `Agent` built fresh per job. Field-filling precedence is spelled out in the instructions, not enforced in code: structured `profile.json` fields used directly → `lookup-learned-answer` tool (fuzzy match via `src/profile/answer-matching.ts`'s `findLearnedAnswer`) → LLM inference from resume/profile context → `ask-human-and-remember` tool (prompt channel + persists via `saveLearnedAnswer`, so a question is never asked twice). A `report-submission` tool takes `{ success, error? }` from the model and, on success, captures the screenshot itself via `browser.screenshot(...)` called directly (not exposed as a model-facing tool) so the image never enters the (text-only) model's context — writes `applications` + updates `jobs.status`, and calls `recordEasyApplyResult(success)` on both branches (batched into the periodic summary notification, not an immediate toast — see `src/notify/summary-aggregator.ts`). `processEasyApplyJob` never rethrows; if `agent.generate()` throws or finishes without the agent calling `report-submission`, it writes a `failed` row itself, so the worker always moves on.

**External-apply automation was removed entirely** (there is no `external-apply-agent.ts`, `external-apply-worker.ts`, or `external-apply` queue). Reasoning: every company's own apply flow (account creation, arbitrary ATS forms, email OTP steps) is different enough that unscripted automation against someone else's site broke constantly. An external job — from either the LinkedIn search agent or career-scan-agent — is instead just recorded (`jobs.status: 'external_saved'`) and counted via `src/notify/summary-aggregator.ts`'s `recordExternalJobFound()`. `needs-input` (any tab's `waitForAnswer`) is the only event that still fires an immediate OS desktop notification (Windows toast via `node-notifier`, in `src/notify/notify.ts` — no click-to-open, that only ever applied to the now-batched `external-job-found`) — `external-job-found` and `easy-apply-result` are batched instead: the aggregator fires one combined summary notification per `notifySummaryIntervalMinutes` (config, default 30) reporting counts since the last flush, skipping the tick entirely if nothing happened.

**Gotcha — any `Agent` with `browser` set needs `noOpBrowserContextProcessor` (`src/agents/no-op-browser-context-processor.ts`):** Mastra auto-attaches a `BrowserContextProcessor` to every browser-enabled agent, and it hard-requires Mastra `memory` plus an active `resourceId`/`threadId` on every call — it throws `[Processor:browser-context] computeStateSignal requires Mastra memory with an active resourceId and threadId` otherwise. Confirmed by reading `@mastra/core`'s `getInputProcessors()` source: it skips auto-adding its processor if the agent's own `inputProcessors` already contains one with `id: 'browser-context'`. The two remaining browser-attached agents (career-scan-agent, easy-apply-agent — the LinkedIn search path no longer wraps an `Agent`/browser at all, see the scan/judge split above) pass `inputProcessors: [noOpBrowserContextProcessor]` — trying to satisfy the real requirement with a `Memory` instance instead pulls in `@mastra/memory`, which as pinned (`1.22.0` against `@mastra/core@1.48.0`) fails at import with `Export named 'parseDuration' not found` — a real version-drift bug in that combination, not a config issue. Model policy: see `model_choice_policy` in the assistant's memory — default `opencode-go/deepseek-v4-flash`, `opencode-go/mimo-v2.5` only for agents that truly need vision.

**Gotcha — `agent.generate()` defaults `maxSteps` to 5 and fails silently:** career-scan and easy-apply both loop over multiple items in a single `generate()` call, and Mastra's default cap of 5 tool-call steps total is nowhere near enough — the agent just stops early with no error, which looks exactly like a prompt-following problem but isn't. Each `agent.generate()` call passes an explicit `maxSteps` sized to the work (career-scan: `Math.max(60, maxJobsPerRun * 8)`; easy-apply: `150`). These are deliberately high-but-bounded, not unbounded — `maxSteps` is the ONLY circuit breaker against a genuinely stuck agent (e.g. repeatedly retrying the same failed click); `easy-apply-worker.ts` sets no BullMQ job timeout/`lockDuration` (`concurrency: 1` only), so an uncapped runaway loop would burn tokens and block every other queued application indefinitely. Don't remove these or bump them to something effectively-infinite thinking they're unnecessary tuning. (The LinkedIn search path has no `agent.generate()` call at all anymore — see the scan/judge split above — so its own circuit breaker is `MAX_PAGES_PER_URL` in `search-agent.ts`, not `maxSteps`.)

## Status

All four phases (TUI shell + login bootstrap, LinkedIn search agent, career-scan agent, easy-apply agent) are implemented. `docs/superpowers/specs/2026-07-14-tui-rebuild-design.md` is the design source of truth and notes where the real implementation deviated from what was originally specced. Nothing has had a real end-to-end run against live LinkedIn/external sites yet — `bun test` covers unit/DB-integration logic only, by design (see the spec's Testing section for why there's no automated e2e against real LinkedIn).
